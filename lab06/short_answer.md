## Half a page: what moto could not prove for you in this lab (think: real backups, real network reachability, TLS), and which integration test covers each gap. 
Moto helps to validate resource configuraiton, launch templates, and policy strutures but it cant simulate the networking, databases engines, or third-party web service behavior.

Moto couldn't validate actual Linux kernel packet filtering, VPC routing tables, or prove that port 3000 is truly blocked from public CIDR access while remaining accessible via the Application Load Balancer. The integration test: test_app_instances_reachable_only_through_alb covers this downside. It attempts a direct TCP connection to the EC2 instance's public IP on port 3000 (asserting a socket timeout/error) while confirming HTTP traffic succeeds through the ALB The follow up test: test_db_port_not_reachable_from_local_computer opens a socket connection directly to DB_HOST:5432 from outside the VPC to prove the PostgreSQL instance is non-routable over the public internet.

Since moto does not spin up a live PostgreSQL server engine. It cannot verify that the Node.js pg driver successfully establishes an encrypted TLS session, nor can it test that server identity is validated against Amazon’s global RDS certificate bundle. The integration test: test_weather_cache_miss_then_hit & test_weather_history_endpoint: both cover this downside. These execute live queries through the Weather service to PostgreSQL, proving the application successfully loads /opt/app/rds-ca.pem, completes the TLS handshake (sslmode: verify-full), and writes/reads cached rows.

Moto instantly returns success for RDS instance calls, but it does not execute AWS engine storage routines. It cannot prove that setting --backup-retention-period 0 actually prevents backup storage billing, nor can it confirm that SkipFinalSnapshot=True and DeleteAutomatedBackups=True leave zero orphan RDS snapshots behind in a live AWS environment.   Integration Test Coverage:test_create_then_delete_db_cleanup: Run against live AWS (or verified in Step 4/Step 10 of Part H), asserting that describe_db_instances, describe_db_snapshots, and describe_db_instance_automated_backups return completely empty arrays after script completion. 

While moto checks whether a user has arbitrary permission attributes in memory, it does not run AWS IAM's actual evaluation logic engine against KMS-encrypted SSM SecureString parameters. The integration test: test_iam_simulate_principal_policy_least_privilege: runs the iam.simulate_principal_policy against deployed IAM roles in your AWS account, proving that the Weather role evaluates to allowed for the DB password and implicitDeny for the Gemini key, while the Advisor role evaluates to the exact inverse.

Since moto cannot execute Node.js application code or mock external HTTP requests to National Weather Service (api.weather.gov), Zippopotam.us, or Google Gemini API servers. It cannot verify timeout handling, User-Agent header validation, or HTML escaping of untrusted AI model output.   The integration test: test_advisor_tier_returns_advice: Confirms real HTTP interaction between the Advisor tier, Weather tier, and Google Gemini model. Additionally, the chaos test, test_chaos_database_cutoff_and_recovery, revokes DB security group ingress on live infrastructure to prove the Weather service degrades gracefully (serving HTTP 200 with cache: "unavailable") rather than crashing. The following chaos test, test_chaos_weather_instance_termination_and_recovery. terminates an active EC2 instance to prove the Advisor handles 502 status codes during the outage and that Auto Scaling recovers within the SLO limit.


## One paragraph comparing the Python and bash versions of the same step (for example creating the database and waiting for it): what was easier to get right, and what was easier to test.
Creating the PostgreSQL RDS instance and waiting for it to actually create had a few differences. Bash allows for simipler AWS commands but Python I needed to translate each line. In bash waiting for the database to create was a simple one line satement but in python you hve to set up a waiter config to run the attempt every 15 seconds until it was actually up. However testing was much easier with python because of moto allowing for testing without needing a live AWS conection.
