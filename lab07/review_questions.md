# Lab 07: Review Questions

| Topic | What this lab did | The question to answer | Answer |
| :--- | :--- | :--- | :--- |
| **Declarative and imperative** | Terraform compares files, state and AWS, then decides the steps | Give one thing the imperative bash version could do that is hard in Terraform, and one thing Terraform did that the bash version never did | Bash makes it easier to interact with environment variables but Terraform allowed for more efficient creation, deletion, and health checks. |
| **State file** | `terraform.tfstate` records every resource and ID | What would happen if you lost it? What would happen if two people applied from different copies? How do teams solve this? | Terraform would lose track the AWS resources its using and may craete duplicates. Two people applying it may cause overlapping or conflicting resources. Teams may store the tfstate in an S3 bucket or separate DynamoDB instance. |
| **Secrets in state** | The Gemini parameter uses `ignore_changes` and the key is stored with the CLI | Where else could a secret reach the state or plan file? Why is a plan file also sensitive? | Secrets can leak via plain-text variables. Plan files can contain parameters and architectural details. |
| **Plan before apply** | `plan -out` then `apply tfplan` | What does reading a plan protect you from? Which plan symbol worries you most, and why? | Reading a plan protects you from unexpected changes. The + or - are the most worrisome as they cause a replace or destroy. |
| **Version pinning** | `~> 5.0` and the lock file | What could go wrong with no version pin, and why do we commit `.terraform.lock.hcl`? | Breaking updates could break entire deployments. But commiting the file we ensure the team is all on the same provider version. |
| **`for_each` or `count`** | Both tiers come from one map, and SSH uses `count` | Why does `for_each` handle removing one tier better than `count` would? | count uses an array and removing an item may cause Terraform to recreate unrelated resources. |
| **Ownership** | Terraform owns a new security group instead of editing lab02's | What goes wrong when a tool and a person both edit the same resource? | This would introduce configuration drift which Terraform will later detect and rever during the next apply |
| **Drift** | You changed a health check by hand | How could a team find drift automatically and regularly? Who should be allowed to change things by hand? | Senior Engineers may be able to change things by hand but only after team conversations. A team could script a regular test every few hours to look for possible drift. |
| **Blast radius** | Changing `cache_seconds` touched only the weather tier | What decides how much one change touches, and how could you shrink it further? | The state file will change how much gets touched. By breaking the state file into separate modules for different app tiers this could shrink blast radius. |
| **Least privilege** | Each role names one resource, and the policy refers to the resource's own ARN | Why is a reference safer than a typed-in ARN? | A reference prevents a possible typo and is better for possible updates or changes. |
| **Terraform and Lambda** | Section 3 and Step 9 | In your own words: what does Terraform have in common with Lambda, and what is the one difference that matters most for how you would use each? | Terraform and Lambda both help setup the infrastructure for a web app but Lambda allows for runtime scaling which probably responds quicker to rapid increases in applicaiton usage compared to Terraform. |
| **Destroy** | One command removes everything | Which resources would you protect from a careless `destroy` in a real environment, and how (look up `prevent_destroy`)? | Databases should be prevented from being destroyed unless there is a backup of the database that can be used |
