# Decision Table
| # | Decision | What I chose and why  |
| :--- | :--- | :--- |
| 1 | Applicaiton architecture | I chose a two-tier architecture consisting of an Advisor tier and a Weather Data tier. This separates application logic from weather data collection and allows each tier to scale independently. It also improves security by limiting the responsibilities and permissions of each tier. |
| 1a | Application Language | I chose Python for the application because it integrates well with AWS services through boto3 and provides useful libraries for API requests, input validation, and testing. Using Python also keeps the application and deployment code consistent. I also have more experience with Python than Node.js | 
| 2 | Weather data APIs | I will continue to use the National Weather Service (NWS) API as the primary weather data source because it provides forecast informaiton for US locations. I will pair this with open-meteo.com which adds the humidity, UV, and visibility. This ensures the applicaiton can provide as much accurate information as possible. | 
| 3 | Zip code lookup and coordinates | I will continue to use the zippopotam api to convert ZIP codes into coordinates. I will pair this with the zipcodes Python library to check for real US zip codes before the API call is ever made.|
| 4 | Morning and night decisions | I chose morning to be 6:00 AM to 6:00 PM  and Night to be 6:00 PM to 6:00 AM matching the NWS logic. |
| 5 | Weather data aggregation | I chose to use the average temperature, average wind speed, lowest visibility, peak UV index, and average humidity for each reporting period. These values provide a useful summary of the weather conditions throughout Morning and Night rather than relying on a single hourly measurement. |
| 6 | Heavy, mild, and no for rain/snow thresholds | I chose to use predefined thresholds in the application's Python code to categorize rain and snow as Heavy, Mild, or No. The categories will be calculated using precipitation probability and measured precipitation amounts. This ensures consistent results and prevents Gemini from making up weather classifications. The final numerical thresholds will be based on documented meteorological sources.|
| 7 | Data caching | I chose to use DynamoDB to cache weather facts and completed reports. Cached weather information will expire after one hour using DynamoDB TTL. This reduces repeated API requests, improves response times, and helps control application costs. | 
| 8 | How Gemini is called (model, answer format, limits) and how its answer is checked | I will create a specific prompt in the app.js that keeps the advice short and concise and that is based off of the users inputed gender and the forecast from the two API sources. 
| 9 | Rule-based fall back advice | Fallback recommendations will be evaluated in Python if Gemini becomes unavailable, reaches its usage limit, or returns an invalid response. This ensures users still receive useful road, clothing, and accessory recommendations even when the AI service is unavailable. Users will be informed of the Python fallback answer rather than Gemini. |
| 10 | Email Delivery service | I chose Amazon SES because it sends messages directly to the specified recipient. Recipient verification and consent will be required before reports are sent. This helps protect user privacy and prevents reports from being delivered to unintended recipients. |
| 11 | Per-tier IAM Permissions | I chose to use separate IAM roles for the Advisor and Weather Data tiers. Each role will receive only the permissions required for its responsibilities. The Advisor tier will access Gemini credentials through SSM Parameter Store, while the Weather Data tier will have access to its required DynamoDB resources. This follows the principle of least privilege.
| 12 | Abuse Controls | I chose to implement input validation, per-visitor rate limits, daily Gemini usage limits, email sending limits, and cached reports. These controls help prevent API abuse, excessive email requests, and unnecessary resource consumption. All external API responses and Gemini output will also be validated and escaped before display. |
| 13 | Daily API limits and budget enforcement | I chose to use DynamoDB to track daily Gemini API usage and enforce the daily call limit. I will also use the budget.py script to monitor infrastructure runtime, API usage, and project expenses. This helps keep the project within the required $2.00 budget. | 
| 14 | Gender Handling and Privacy | I chose to provide inclusive gender/clothing categories, including a neutral option. Gender will only be used to customize clothing recommendations and will not be sent to weather APIs, stored with email addresses, or written to application logs. This minimizes the collection and exposure of personal information. |
